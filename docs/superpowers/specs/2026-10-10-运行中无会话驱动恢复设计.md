# 运行中但无会话驱动的恢复设计

## 问题与证据

宿主重启后，SQLite 中仍保留目标为 `RUNNING`、节点为 `PENDING` 和任务—会话绑定；但进程内的执行父会话对象与后台调度循环已消失。当前页面只从节点状态推断“等待会话继续”，没有把这个状态作为可执行控制呈现，因此既不会向已绑定会话发送 `long_task_resume`，也没有明确的手动恢复入口。用户看到“运行中”，实际上没有节点在运行。

这不是某个任务的特殊状态：任何运行中的目标在宿主重启、后台循环异常退出或 Web 侧确认后缺少活父会话时都可能出现。

## 目标

1. 运行时以单一、可测试的派发需求字段表述“需要活会话驱动”。
2. 任务条和任务区将该字段显示为“等待会话继续”，提供明确的继续入口。
3. 当前会话正是持久绑定会话时，页面仅自动注入一次继续指令；失败时保留可重复点击的手动入口，不能静默吞掉失败。
4. 会话在别处时不擅自跳转页面，只提示用户前往绑定会话继续；未绑定会话时提示先附加会话。

## 非目标

- 不把已经消失的 DSH `Agent` 对象序列化或伪造恢复；该对象只能由一个当前活会话重新提供。
- 不修改 DeepSeek Harness 源码或用户 profile。
- 不替用户回答模型提出的研究范围、权限或资料选择问题。

## 不变量

- `requiresSessionDriver` 只在目标为 `RUNNING`、存在未结算节点、没有运行节点且本进程没有该目标后台循环时为真。
- 有后台循环（包括重试等待期）时，该字段必须为假，避免重复派发。
- 自动注入以“任务 ID + 控制修订号”为键，每个页面生命周期最多一次；手动按钮始终可再次尝试。
- 继续指令必须发送到持久绑定的当前会话，不能发送到任意历史会话。

## 验收

- 单元测试覆盖宿主重启后的 `RUNNING + PENDING` 目标、活后台循环、无绑定会话和异会话四种状态。
- 构建产物被重新生成；部署后，现有任务若满足条件，任务条显示“等待会话继续”并能向绑定会话投递一次继续指令。
