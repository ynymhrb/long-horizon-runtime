# 会话驱动注入去重修复实施计划

**背景结论（已取证）**：用户在任务区点一次「继续任务」或「确认执行」，浏览器会把同一条驱动消息重复注入绑定会话。

- 持久层只发生一次控制动作：07:28:35 一次 `PlanConfirmed`，10:48:28 一次 `GoalResumed`（`long-task-runtime.sqlite`）。
- 会话日志同一时刻出现 2~3 条 `agent/inbox/spliced` 插入，`rpcId` 各不相同（`session-820ea710…`）。
- 用真实客户端源码 + jsdom 复现：点「继续任务」注入 3 次（+3ms/+6ms/+2696ms），点「确认执行」注入 2 次（+4ms/+2681ms）。

**根因**：驱动入口有三处、去重状态三份，且显式路径不登记去重键。

1. `client/TaskCockpit.js` 自动驱动 effect，去重键 `${task.id}:${task.controlRevision}`，集合是组件内 `useRef`；
2. `client/TaskCockpit.js` `guideAfterResume` 显式路径，成功注入后不登记该键，同一 revision 因此被注入两次；
3. `client/TaskStrip.js` 任务条自带一份 `useRef` 与 3 秒轮询，独立再注入一次。

`client/index.js` 的 `driveInSession` 每次调用都执行 `session.prompt(..., 'queue')`，宿主对每次 prompt 都写入一条独立持久用户消息，`queue` 模式下多余消息就停留在输入区成为「排队消息」。

## 目标不变量

- **一个 (会话, 任务, 控制版本) 只允许一次自动注入**，跨组件、跨重挂载、跨轮询周期都成立。
- **进行中的注入不可被并发重复**：第二次调用在同一次事件循环内就被判定为跳过。
- **注入真实失败必须可重试**：宿主拒绝或抛错后，下一次自动/人工尝试仍然可以发送。
- **人工不应被永久锁死**：注入成功但代理长时间无响应时，超过宽限期允许用户重新发送。
- **不引入第二处去重**：组件内不再保存 `automaticallyDriven` 之类的本地集合。
- 驱动消息文本、`queue` 模式、`resumeDriverMode` 的 inject/open/attach 语义保持不变。

## 风险与不做的事

- 不改宿主 prompt API，不在持久层做消息去重：去重的语义边界是「同一个控制版本只自动驱动一次」，属于客户端驱动职责。
- 不引入 jsdom 作为测试依赖：组件级验证继续用 `tmp/repro/drive-double.mjs` 复现脚本，仓库测试保持零 DOM 依赖。
- 已有历史会话里已经排队过的重复消息不会自动清理，属于既往数据；本次修复只阻止新重复产生。
