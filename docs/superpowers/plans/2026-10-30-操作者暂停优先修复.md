# 操作者暂停优先（Operator Pause Authority）实施计划

## 已取证的问题

用户在任务条点「暂停」后，任务在几十秒内又自行恢复运行。

**证据（`long-task-runtime.sqlite` + 绑定会话日志 `session-820ea710-58b1-4b39-9b96-c64f288ce5a3`，时间为 UTC，本地 +8h）**

| 时间 | 事件 | 来源 |
|---|---|---|
| 16:41:56.81 | 驱动消息注入 → turn 开始 | Web UI（用户点「继续任务」） |
| 16:42:02 | `GoalPaused{reason:'user_requested'}` + 控制版本 8 + attempt 中断 | Web UI 暂停 |
| 16:42:28.09 | 模型 `tool/call long_task_resume` → `GoalResumed{}`（无控制版本推进）→ 第 4 轮 + 新 attempt | **模型工具** |
| 16:42:32 | `GoalPaused` + 控制版本 9 + attempt 中断 | Web UI 再次暂停 |
| 16:43:19.72 | 模型 `tool/call long_task_resume` → `GoalResumed{}` → 第 5 轮 + attempt `a2641fe6` **持续运行 57 秒** | **模型工具** |
| 16:43:27 | 模型自述「这次执行轮次真正启动并保持运行」 | — |

即：**暂停确实生效了，但随后被代理的一次 `long_task_resume` 覆盖**。用户观察到的「还在跑」是第 5 轮在运行（该 attempt 已由本次处置在 16:44:16 中断，控制版本 10，状态 PAUSED）。

## 根因

1. **判定点没有授权区分**：`src/runtime.ts:163` 的 `resumeGoal` 只校验 `state ∈ {PAUSED, RUNNING}`，不关心是谁在恢复；`src/tools.ts:145` 的 `long_task_resume` 因此可以把操作者刚暂停的任务直接拉起。
2. **状态写入点不可区分来源**：`src/runtime.ts:206-212` 的 `pauseGoal` 对所有调用者写同一个 `reason: 'user_requested'`，Web UI 暂停与模型暂停在持久层长得一模一样，无法据此建立「操作者暂停需操作者恢复」的不变量。
3. **相邻生命周期入口同样无授权区分**：`src/runtime.ts:333` 的主机重启恢复（`recover`）与 `:346` 的额度恢复定时器都会对 PAUSED 目标直接 `resumeGoal`，同样会覆盖操作者暂停。
4. **驱动消息语义过强**：`client/task-model.js` 的驱动消息要求「立即调用 long_task_resume…无需再向我确认」，同一条消息在长 turn 内被再次采纳时就会覆盖更新的暂停；上一轮已消除重复注入，但单条消息的过期语义仍在。
5. **客户端静默失败**：`client/TaskStrip.js` 的 `update()` 用 `.catch(() => undefined)` 吞掉所有失败与 `conflict`，若暂停因控制版本冲突未生效，界面不会告诉用户。

## 目标不变量

- **操作者暂停是粘性的**：`PAUSED` 且暂停来源为操作者时，任何非操作者来源的恢复都必须被拒绝，并留下可审计证据。
- **来源持久化**：`GoalPaused` 记录 `origin: 'operator' | 'agent' | 'system'`，投影为 `pause_origin`，恢复时清空。
- **授权按调用面传递**：浏览器任务区（Typert 远程）为 `operator`；模型工具与子代理为 `agent`；调度器自愈、额度恢复、主机重启恢复、后台看门狗为 `system`。
- **不误伤合法流程**：代理自己暂停、或因自动重规划失败/会话停止而暂停的任务，仍允许代理恢复。
- **失败可见**：客户端暂停/恢复失败或版本冲突必须在界面上显示，禁止静默吞掉。
- 既有数据库升级幂等，历史 `pause_origin` 为空的行按 `system` 处理（不追溯拦截）。

## 风险与边界

- 只影响暂停/恢复授权，不改变确认、取消、改目标语义。
- 历史暂停行（`pause_origin` 为空）按 `system` 处理，不追溯拦截，避免把旧任务永久锁死。
- 拒绝恢复是显式错误而非静默忽略，模型会收到可读原因并向用户转述。
- `recover()` 的扫描范围仍由 `scheduler.recover()` 决定（只有存在运行中 attempt 的目标才会进入循环）；本次只保证进入循环后不覆盖操作者暂停。
